# data/real-pilot/

- `scottsdale-real-snapshot.json` — the identity data
  `apps/consumer-web/real-pilot.html` and the pipeline both read: id, name,
  address for 139 restaurants (as of 2026-09-01). The original 7 are
  hand-researched with a source citation each; the other 132 came from
  `discover-restaurants.mjs` (see below), reviewed by hand before being
  added, each carrying a pre-resolved `place_id` so their first pipeline
  run skips a redundant Google Places lookup. This file is deliberately
  NOT where scores, ratings, or review counts live -- that's
  `scottsdale-live-scores.json`, generated fresh by the pipeline, never
  hand-edited alongside this one.

- `scottsdale-live-scores.json` — **generated, not committed by hand.**
  Produced by `services/agents/source-ingestion-agent/run.mjs`, which the
  daily and weekly GitHub Actions jobs run. `apps/consumer-web/real-pilot.html`
  merges this with `scottsdale-real-snapshot.json` at page-load time:
  every restaurant with a real entry here (`confidence > 0`) renders its
  live score, factor breakdown, delta, and dish/service mentions; every
  restaurant without one yet renders an honest "Not yet scored" placeholder
  rather than a zero or a guess. Each restaurant here also carries `lat`/`lng`
  (real, Google-geocoded, refreshed daily at zero extra API cost --
  see the comment above `fetchGooglePlaces()` in `run.mjs` -- replacing
  the original 7's hand-picked neighborhood-center approximations) and
  `previous_score`/`score_delta`/`delta_since` — a real day-over-day
  change, computed from `score-history.json`, not a demo placeholder.
  `dish_mentions` and `service_mentions` (weekly, derived-only term counts
  from the restaurant's own up-to-5 Google reviews -- food terms and
  service/experience terms respectively, same extraction method, see the
  DISH MENTIONS comment in `run.mjs`) and `recent_reviews` (the overall
  average star rating of that same review sample, no text involved) are
  all free -- they reuse the one Places Details call already made for dish
  mentions, no new API cost. Never hand-edit it; any sandbox/test run's
  output must be deleted before packaging, same discipline as always.

- `discovered-candidates.json` — **generated by a separate, manual-only tool
  (`services/agents/source-ingestion-agent/discover-restaurants.mjs`, run
  via the "Discover Restaurants" workflow), not part of the daily/weekly
  pipeline and not auto-merged into `scottsdale-real-snapshot.json`.** A
  real, Google-verified candidate list (name, address, place_id, rating)
  for expanding the roster, meant to be reviewed and hand-curated into the
  real snapshot rather than dumped in wholesale -- Google's "restaurant"
  category also catches some coffee shops, bars, and ghost kitchens.

- `api-usage-ledger.json` — **also generated, not committed by hand.** The
  real, running count of every metered Google API call this pipeline has
  made -- placesTextSearch/placesDetails (monthly) and customSearch (daily) --
  kept so the budget guard in `run.mjs` always knows exactly how many calls
  have been made against each free tier before it will make another one.
  Updated only on a run that completes fully; a run the guard hard-stops
  exits without touching any file in this folder, so old data always stays
  exactly as it was until someone checks why it tripped. See the "Budget
  guard" comment near the top of
  `services/agents/source-ingestion-agent/run.mjs`.

- `score-history.json` — **also generated, not committed by hand.** The
  system's actual memory: one score per restaurant per UTC calendar date,
  written and appended to by the same script on every run, capped at 180
  days per restaurant. This is what `previous_score`/`score_delta` in
  `scottsdale-live-scores.json` are computed from. Same rule as above —
  a sandbox test run produces real-looking dated entries for real, named
  restaurants using fabricated/zero data, so any file this session
  generates while testing gets deleted before packaging, same as
  `scottsdale-live-scores.json` always has. The first entry appears after
  the first real run on GitHub; it takes two real daily runs on two
  different days before `score_delta` stops being `null`, since a delta
  needs a "yesterday" to compare against — that's expected, not a bug.
